**ОТЧЁТ ПО ЛАБОРАТОРНОЙ РАБОТЕ №1**  
**Тема:** Каркас FastAPI-приложения и базовый REST API (Вариант 2: Интернет-магазин)

**1\. Цель работы**  
Получить практические навыки создания веб-приложения на фреймворке FastAPI, настройки маршрутов, использования Pydantic-моделей для валидации данных и реализации базового CRUD-интерфейса (создание, чтение, обновление, удаление) без использования базы данных, с хранением информации в оперативной памяти, для предметной области «Интернет-магазин».

**2\. Структура проекта**  
Проект имеет модульную структуру, разделенную по слоям ответственности. В корневой папке находится файл зависимостей и главная директория приложения. Внутри папки приложения (app) находится главный исполняемый файл main.py, который инициализирует FastAPI и подключает общий роутер. Логика разделена на директории: api (где версионируются маршруты, в частности папка v1 с эндпоинтами для товаров), schemas (содержит Pydantic-классы для описания и валидации структуры данных) и services (содержит бизнес-логику и временное хранилище данных в памяти).

**3\. Листинг основного кода (Описание реализации)**  
В файле схем описаны классы для валидации. Базовый класс содержит обязательные поля: наименование, цена (с ограничением больше нуля), категория, количество на складе и статус. Схема для обновления допускает частичное изменение полей. Схема для ответа добавляет системные поля (уникальный идентификатор, даты создания и обновления).  
В сервисном слое реализован класс, который имитирует базу данных. Он использует словарь для хранения товаров в памяти и счетчик для генерации идентификаторов. Методы сервиса позволяют получить список всех товаров, найти один товар по ID (с выбросом исключения, если его нет), создать новую запись, обновить существующую и удалить товар.  
В файле маршрутов создан роутер с префиксом для товаров. Каждый эндпоинт обращается к методам сервиса. Обработка ошибок реализована через перехват исключений сервиса и возврат стандартных HTTP-ответов (например, 404 Not Found).

**4\. Скриншот /docs**  
_(Сюда необходимо вставить скриншот интерфейса Swagger UI, открытого по адресу [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs), где виден список доступных методов для работы с сущностью «Товар»)_

**5\. Примеры запросов и ответов**  
При создании товара (POST-запрос) клиент отправляет JSON-объект с названием, описанием, ценой, категорией и количеством. Сервер валидирует данные и возвращает статус 201 Created с полной информацией о товаре, включая присвоенный ID и временные метки. При запросе списка товаров (GET) сервер возвращает статус 200 OK и массив объектов. При обновлении (PUT) передаются только те поля, которые нужно изменить (например, цена или количество), а сервер возвращает обновленный объект. При удалении (DELETE) сервер возвращает статус 204 No Content без тела ответа.  
Если запросить товар с несуществующим ID, сервер вернет ошибку 404 Not Found с сообщением о том, что объект не найден. Если при создании передать отрицательную цену или пустое название, сработает валидация Pydantic, и сервер вернет статус 422 Unprocessable Entity с подробным описанием полей, которые заполнены неверно.

**6\. Выводы**  
В ходе выполнения работы был разработан функционирующий каркас веб-приложения для интернет-магазина на фреймворке FastAPI. Были изучены принципы маршрутизации и обработки HTTP-запросов. Реализован базовый CRUD-интерфейс для управления товарами. С помощью Pydantic настроена надежная валидация входящих данных, исключающая попадание некорректной информации в систему. Реализована корректная обработка HTTP-статусов ответов. Разделение кода на слои (маршруты, схемы, сервисы) обеспечивает чистоту кода и создает прочную основу для перехода к работе с реальной базой данных во второй лабораторной работе.


ОТЧЁТ ПО ЛАБОРАТОРНОЙ РАБОТЕ №2  
Тема: Подключение базы данных и реализация CRUD через SQLAlchemy (Вариант 2: Интернет-магазин)  
  
1\. Цель работы  
Научиться подключать базу данных к FastAPI-приложению и реализовывать операции создания, чтения, обновления и удаления (CRUD) с использованием ORM-библиотеки SQLAlchemy. Заменить хранение данных в оперативной памяти на долговременное хранение в базе данных.  
  
2\. Схема подключения к базе данных  
Для работы была выбрана база данных SQLite, так как она не требует установки отдельного сервера и хранит все данные в одном локальном файле. Для обеспечения асинхронной работы приложения используется движок aiosqlite.  
Настройки подключения вынесены в отдельный файл переменных окружения .env (переменная DATABASE\_URL). В коде создан модуль для управления сессиями базы данных, который предоставляет функцию-зависимость для получения асинхронной сессии в маршрутах FastAPI. Для создания таблиц при запуске приложения используется механизм событий жизненного цикла (lifespan), который автоматически выполняет миграцию структуры таблиц при старте сервера.  
  
3\. Код модели  
Вместо словарей Python, данные теперь описываются с помощью декларативных моделей SQLAlchemy. Создан класс модели «Товар» (Product), который наследуется от базового класса. В модели описаны колонки для хранения: уникального идентификатора (первичный ключ), названия, описания, цены, категории, количества на складе и статуса. Также добавлены служебные поля для автоматической записи даты и времени создания и обновления записи. Типы данных колонок строго соответствуют языку SQL (строки, числа с плавающей точкой, даты).  
  
4\. Код зависимости для сессии  
Для того чтобы каждый HTTP-запрос работал с базой данных в изолированной транзакции, была создана асинхронная зависимость. Она открывает новую сессию подключения к базе данных перед выполнением запроса и гарантированно закрывает её после отправки ответа клиенту. Маршруты (эндпоинты) получают эту сессию через встроенный механизм внедрения зависимостей FastAPI, что обеспечивает чистоту кода и предотвращает утечки соединений.  
  
5\. Примеры запросов и ответов  
При отправке POST-запроса на создание товара данные проходят валидацию в Pydantic, после чего сервисный слой создает объект модели SQLAlchemy, добавляет его в сессию и фиксирует изменения (commit). Сервер возвращает созданный объект с присвоенным базой данных ID. При GET-запросе списка товаров выполняется асинхронный SQL-запрос через метод execute, результаты преобразуются в Pydantic-схемы, и клиент получает JSON-массив. Запросы на обновление и удаление работают аналогично: сначала происходит поиск записи в базе по ID, затем её изменение или удаление с последующим сохранением.  
Обработка ошибок также была скорректирована: если запрашивается товар с несуществующим ID, выполняется поиск в базе данных, и при отсутствии записи выбрасывается исключение, которое FastAPI преобразует в ответ 404 Not Found.  
  
6\. Выводы  
В ходе выполнения лабораторной работы приложение было успешно переведено с хранения данных в памяти на работу с реляционной базой данных. Была настроена асинхронная работа с SQLite через SQLAlchemy и драйвер aiosqlite. Настройки подключения вынесены в переменные окружения, что соответствует лучшим практикам разработки.  
  
Была спроектирована модель данных, описаны типы колонок и настроено автоматическое создание таблиц при старте. Сервисный слой был переписан для взаимодействия с базой данных через асинхронные сессии, а маршруты FastAPI — для внедрения этих сессий через зависимости. Теперь данные не теряются после перезапуска сервера, что делает приложение более надежным и приближенным к реальным production-условиям.
